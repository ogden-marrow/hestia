# Hestia threat model

Status as of 2026-11-12. Written from the red-team review of 2026-11-10 and what has been fixed since. Every row names the issue or PR that holds the evidence. A release is gated on the checklist at the end.

## What we protect

| Asset | Why it matters |
|---|---|
| Secrets on the computer (SSH and GPG keys, tokens, passwords, sessions, browser and mail data) | Theft is the worst outcome; Hestia must never read, copy or send them. |
| The person's files and what they are called | Names alone can be private. They must not leave the computer except into the person's own private repository, and never reach a remote model. |
| The home repository | Holds how the computer is set up. If it were public, or if what it contains ran code on every machine, that is a compromise. |
| The GitHub token | Gives access to the person's private repositories. |
| The computer's integrity | Hestia moves and copies files and can restore a machine; a bug there can destroy data. |

## Who and what we defend against

1. **A stranger who can put a file on the computer** (a download, an attachment, a shared folder). They control file names and contents.
2. **A malicious or compromised repository** that Hestia is pointed at or restores from (a poisoned home repository, a public fork, a changed dependency).
3. **Another program running as the same user** (it can read the user's files and processes anyway; we only avoid making that easier).
4. **A careless moment by the person** (publishing the wrong repository, pushing a secret, a wrong click).
5. **A network attacker** between the computer and GitHub.
6. **A supply-chain attacker** (a compromised crate, GitHub Action or release).

Out of scope: an attacker with root, a compromised desktop session or keyring, physical access to an unlocked machine, and GitHub itself being malicious.

## Trust boundaries

- **Computer to GitHub:** only commits to the person's own private repository, only after a scan, only over https with the person's token.
- **Computer to model:** only the local model on loopback. File names reach it, so names are treated as hostile data.
- **Repository to computer:** restoring brings in untrusted content. Nothing that runs by itself is restored without an explicit flag.
- **GitHub token:** lives only in the system keyring.

## Threats and what stops them

| # | Threat | Mitigation | Status | Evidence |
|---|---|---|---|---|
| T1 | A secret is committed and pushed | One shared scanner (modern token formats, vendor tokens, JSON-quoted and bare `PASSWORD=` values, command-line flags, binaries, any case) runs on everything captured and on the new commits before every push; secret lines are left out of the backup, private keys drop the whole file. The range scan reads the hunk headers, so an added line starting `++` is still scanned, and merge commits are scanned against their first parent | Fixed | #62, #80, #107, #129, #175 |
| T2 | The scanner misses a secret (short, unusual format, encoded) | Scanner is a filter, not a guarantee; the allowlist captures only named files; the push is restricted to a private repository. Known gaps: placeholders that look like values (`PASSWORD=changeme`) are flagged, values under 8 characters are not, and a secret split over two lines is not seen | Residual risk | #129, #175; keep adding rules |
| T3 | Pushing to a public, foreign or renamed repository | The push target is checked on the address git will really use (after pushurl and insteadOf), must be a private repository of the signed-in person; redirects and odd answers fail closed | Fixed | #80, #122, #132 |
| T4 | Publishing a leaky history | Whole history scanned before any create or push | Fixed | #62, #121 |
| T5 | Capture deletes or overwrites the person's live files | New copy built beside the old and swapped in; live symlinks into the repository are followed to their target; a capture that would keep under half of the last one is refused | Fixed | #99 |
| T6 | The mover follows a symlink, races, overwrites or files into a hidden folder | Plain files only, no symlinks at either end, exclusive temp file, publish without replacing, hidden destinations refused. Folders: a rename only (never copy and delete), refused over an existing destination, through a symlink anywhere on either path, into itself, across disks or a mount point, outside home, hidden, or over a sensitive path; a new folder is one empty directory; every change is journaled, and undo treats the journal as untrusted, never overwrites, and removes a new folder only while it is still empty (never recursive) | Fixed | #65, #66, this PR |
| T7 | The repository controls code that runs on every machine | The watcher ships with Hestia, not in the repository. Restore is a dry run by default and copies instead of linking. It goes file by file (a different existing file is kept as `.bak`, nothing is skipped by folder), writes only names on a fixed list, never touches `~/.ssh`, `~/.gnupg` or the keyring, ignores symlinks and paths that leave the home folder, restores file and folder modes without setuid or group/other write, and holds back everything that runs or changes what runs (shell startup files, `.gitconfig`, `environment.d`, autostart entries, systemd user units, fish/zsh/bash config, shortcut commands) until `--allow-executable`. The summary counts what was restored, identical, replaced and skipped. Tested against a poisoned repository (`tests/bootstrap.sh`) | Fixed | #63, #108, #174 |
| T8 | Desktop history and accounts end up in the backup | Desktop settings are captured by an allowlist of sections, dropping keys that remember what you did; the never-capture list also applies to files inside captured folders (a bookmarks file, a token-named file), which are dropped from the copy only | Fixed | #116 |
| T9 | The clipboard history keeps secrets | Off until turned on, filters codes and tokens, file readable only by the person, pruned, deleted when turned off | Fixed | #105, #106 |
| T10 | A hostile file name steers the model | Names reach the model only as cleaned, shortened JSON data it is told to treat as data; its answer is limited to the known kinds; names are cleaned before embedding | Fixed | #125 |
| T11 | File names or contents leave the computer through the model | The model host must be loopback, with no user info and no redirects | Fixed | #64 |
| T12 | The GitHub token leaks | Only in the system keyring, refused when there is none, never printed, logged, put on a command line or in a file; git gets it through a credential helper that answers only for github.com over https; no redirects; base URLs overridable only to loopback | Fixed | #118 |
| T13 | Three lists of "never capture" drift apart | One deny-list read by capture, the Machine screen and the starter manifest. It names credential files and profiles (npm, pip, docker, kube, cloud CLIs, rclone, cargo, terraform, VPN, browsers, chat and password-manager apps), shell histories, `.Xauthority` and every private key type, and refuses a parent folder that holds any of them (`~/.config`, `~/.docker`, the home folder) so adding it wholesale cannot carry them along | Fixed | #129, #175 |
| T14 | A bulk action is triggered by a deceptive name | "Answer similar folders together" is off until chosen | Fixed | #131 |
| T15 | A compromised dependency or CI action | Every action is pinned to a commit; Dependabot proposes updates; cargo-deny blocks a dependency from an unexpected registry or git source or under a licence we have not allowed, and reports known advisories (three 'unmaintained' notices, no vulnerabilities: #135) | Mitigated | #59, #135 |
| T16 | Releases are not verifiable | Release files carry SHA-256 checksums and a signed build attestation (GitHub artifact attestation: `gh attestation verify <file> --repo ogden-marrow/hestia`); the release workflow reads by default and only its job can write; every action is pinned to a commit; checkout leaves no credentials behind. The packaging is rehearsed in CI (`tests/release-rehearsal.sh`) but the signing and attestation steps only run on a real tag: no release has been cut | Mitigated (untested until the first release) | #12, #59 |
| T17 | A private home repository is published by mistake | Publishing is never automatic; the person's repository is created private and verified private before every push | Mitigated | #121, #122 |
| T18 | Uninstall leaves things behind, or an install writes an unsafe unit | Uninstall removes programs, units and overrides, always deletes the clipboard history, gives Alt+Space back, and only `--purge` deletes settings; install refuses path characters that could change a systemd unit; the launcher ignores toggles while the screen is locked | Fixed | #60 |
| T19 | The public repository holds personal data | Files are checked in CI (`tests/privacy.sh`: home paths, email addresses, this computer's user and host name); fixtures read no real data; test tokens are built at run time. **Accepted by the maintainer (2026-11-11): their real name and email are public, so GitHub merges may carry them on commits.** The identity check on commits is a note, not a failure (`PRIVACY_STRICT_IDENTITY=1` makes it strict for a project that wants a hidden identity) | Accepted | #61, #142 |
| T20 | Sign-in uses a broader permission than needed | GitHub's `repo` scope is the narrowest that can create a private repository; a narrower mechanism (a GitHub App on one repository) is to be investigated | Residual risk | #110 |
| T21 | The GitHub CLI fallback in the watcher checks "private" but not owner | Disappears when Hestia sign-in is live | Residual risk | #110 |
| T22 | The backup stops working and nobody knows (a commit, push or capture fails quietly; a push rejected for ever after another computer pushed; a stale `index.lock`; a hung push holding the lock; a busy computer skipping for ever) | Every git call is checked and the tree must be clean afterwards; a failure is a `watch.json` result that starts `FAILED` with the first line of the reason (offline, signed out, repository gone, repository public are told apart); the push first fetches and rebases onto the other computer's commits; a stale lock is cleared after 10 minutes; fetch and push time out and the unit has `TimeoutStartSec`; waiting for a quiet moment stops after 6 hours; a second run says it was refused (exit 75). The UI still shows a raw git line, not this result (not yet fixed) | Mitigated | #166, #167, #172 |
| T23 | One bad file wedges the backup (over GitHub's 100 MB limit; unreadable; an apostrophe or `#` in a path; a mass-deletion guard that never lets go) or a hostile name hides a secret (a newline in the name) | Files over 50 MB and unreadable files are skipped and listed in `SKIPPED.txt`; the scanner streams, reads path and rule NUL-separated, and exits 2 (could not look) apart from 1 (found); an unsent commit that holds a possible secret is redone from what GitHub has, from the cleaned working files; the deletion guard is lifted by a changed capture list or by `touch .accept-smaller-capture`; names with spaces or non-ASCII letters are read with NUL separators. The UI "add path" box still accepts what the list cannot hold (not yet fixed) | Mitigated | #168, #169, #170, #171 |
| T24 | Capture stores less, or more, than the person meant (the capture list is re-seeded on an OS upgrade; a symlinked dotfile is stored as a link with no content, or a link is followed to a file outside the home folder or on the deny-list; a cloned folder becomes a gitlink with no files; deb822 `.sources` apt files are missed) | One capture list survives version changes (a new version folder starts from the nearest other version's list); a symlinked path or a link inside a captured folder is captured by its target's content only when the target is a file inside the home folder that the deny-list allows (the copy is then scanned like any file), otherwise it is left out and listed in `SKIPPED.txt`; `.git` folders are never copied, so a nested clone is stored as its files; `*.sources` are captured and restored like `*.list` (the distribution's own `ubuntu.sources`/`debian.sources` are not) | Fixed | #173 |
| T25 | The activity feed (`lifestream feed`) becomes a new way to read or leak something: a tampered journal, undo log or watcher history names a path outside the home folder, a hidden or secret place, or smuggles control or direction-changing characters; a huge file makes it slow or noisy | The feed is read-only (it opens its three sources for reading and writes nothing). Every line is untrusted: it must parse, carry a real timestamp, and name only plain visible paths inside the home folder by the same test undo uses, otherwise the line is skipped (never fatal, never printed). It prints relative paths the journal already holds, never file contents, hashes or secrets; text is stripped of control and direction characters and bounded; at most 5 paths per item, 1000 items and 512 KB of output, and only the newest 4 MB of each source is read. The watcher history keeps only the result sentence the Backup chip already shows | Fixed | #237 |
| T26 | A person who never opens Hestia never learns the backup keeps failing (or has quietly stopped), or the warning itself is noisy or leaks: a notification on every failed run, one per run for days, a path or token in its words, one that ignores the person's "off" | One policy in the engine, `lifestream backup-state`, reads the watcher's own files and decides: `failing` (the latest runs failed), `stale` (no successful run for 36 hours) or `ok`; garbage or missing files are `unknown` and never notify. A notification is due only when a problem has lasted 6 hours and that episode (its first failing run) was not already told (`notified.json`), so a failure that outlasts the 200-run history is still one episode; the watcher sends ONE `notify-send` and only then records it; the episode is forgotten when the backup works again, with one quiet "working again" only if a failure was told. The sentence is chosen from a fixed list by the kind of failure, never copied from the watcher's text, so it holds no path or secret. `notifications=off` in the settings file turns it off. The tray shows the same state (warm flame, tooltip). A dead timer is seen by the tray and the app but cannot send a notice itself (the watcher is not running) | Mitigated | #225 |
| T27 | A backup that cannot be restored is found out on the worst day, or a restore that is no longer safe goes unnoticed (a bug in restore, a poisoned repository, a corrupted manifest) | Once a week `rehearse.sh` (`hestia-rehearse.timer`, weekly, `Persistent`, randomized, idle priority, not on battery) copies the repository's HEAD into a private scratch folder (mode 700, removed however it ends), runs the one restore (`bootstrap.sh`) against a fake home there as a dry run and then for real, and checks: the manifest and capture list parse; every file placed has the repository's content hash and mode (no setuid, no group/other write); no link was restored or followed; nothing that runs by itself, no key, keyring or login file was written; nothing outside the fake home changed (a sentinel folder, the repository copy and the real home's key and startup files are listed before and after); the shared secret scanner finds nothing. It never targets the real home and never runs the package or desktop-settings steps. The result (`rehearsal.json`) holds only fixed plain sentences: no paths, contents or secrets. A failed or two-week-old check is a second line in `backup-state`, never a failing backup. The rehearsal checks the restore that ships with Hestia against the repository as pushed; it does not prove that packages and desktop settings restore, or that a different machine would restore the same | Fixed (files and config); packages and settings are not rehearsed | #226 |
| T28 | Self-update becomes a way in or a way to break the computer: it fetches from a repository that is not Hestia's, sends credentials, runs while a backup is half done, overwrites the person's own changes in the checkout, installs a build that does not start, leaves no way back, or deletes more than its own files | `lifestream update` fetches only from the public Hestia repository over https (the address git will really use, after `insteadOf`, must match exactly; tests override it with one variable), with no credential helper, no prompt, no redirects and a 20-second limit; it is the only network use and nothing else is sent. `check` never touches the checkout's working tree. `apply` and `rollback` take the watcher's and the restore check's own `flock` locks (refusing while either runs, holding them to the end) and refuse a checkout with changes or commits of its own or off `main`; the checkout only fast-forwards (never reset, merge commit or force). Each build goes in its own folder; the new one must pass a start-up check (`lifestream --version`, `hestia --list-scenes`) before one atomic link rename switches to it, and until then the old build stays installed; exactly one previous build is kept for `rollback`. Only build folders inside `<prefix>/lib/hestia/builds` are ever removed; the person's data, settings and home repository are never touched; `uninstall.sh` removes the builds and `install.json`. A timer is restarted only when its unit changed. The build runs the checkout's own `install.sh` and `cargo`: an update is exactly as trusted as the code it installs (the public repository's `main`); releases will add signatures (#244) | Mitigated (a compromised public repository is trusted, as it is on a manual `git pull`) | #265 |

## Residual risks we accept, and why

- **The maintainer's real name and email appear on merge commits** made by GitHub (#142). The maintainer is a public person and chose to accept this; it is not a leak. Contributors who want a hidden identity should use GitHub's 'Keep my email addresses private'.
- A secret the scanner cannot recognise can still reach the person's own private repository. The repository stays private and the person can rewrite it; we do not claim otherwise in the product.
- The person's own GitHub account is the root of trust for backups. If it is compromised, so is the backup.
- The system keyring is trusted: any program that can unlock it as the same user can read the token.

## Release gate

A release is blocked unless all of these hold:

1. No row above is **Open** with a severity of high or critical (T16 must be exercised by a real release and verified before the first public release).
2. `cargo test --workspace` and every shell test pass in CI on a clean runner.
3. The secret scanner finds nothing in the repository's history, apart from the named test fixtures.
4. A clean-machine install and first run has been done end to end (#6).
5. This file is updated in the same change as any change to what leaves the computer, what is read, or what runs by itself.
